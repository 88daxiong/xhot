WeKnora：把文档编成可引用知识，再交给问答与 Agent

物理本质：它是一套企业知识平台，而不是「又一个 Embedding 封装」。一份文件先作为知识条目落库并写入对象存储，再经异步任务解析、切块、写入块表，并（在开启索引时）同步派生到向量/关键词引擎。提问时按租户与知识库授权做混合检索，用加权重排融合把分数折到 [0,1]，再经可选重排、合并与截断，把通过的块变成模型上下文里的可引用证据，最后流式生成。

它到底在解什么问题

组织里的知识分散在 PDF、Office、Wiki、网盘和聊天里。人要的不是「把文件存进去」，而是：问一句能得到可核对来源的回答，复杂任务能走多步 Agent，并且同一套知识还能整理成 Wiki。README 把产品分成 RAG、Agent、Wiki 三条模式，共享知识库。作者宣称

从源码看，真正的闭环是两条控制流：文档处理任务（asynq 上的 ProcessDocument）把字节变成块和索引；问答管道（sessionService 动态组装的事件列表）把问题变成检索证据再生成。Agent、MCP、IM 渠道是同一管道和同一知识库上的适配器，而不是另一套存储。源码确认

真源与派生（必须分开说）

  • 原始对象：上传或同步得到的文件保存在可替换的对象存储里，知识行记下 file_path、file_hash、file_size。源码确认 migrations/mysql/00-init-db.sql:65–90
  • 知识条目：knowledges 是这份文档在系统里的身份，带 parse_status、enable_status、租户与知识库外键。它不是检索单元。
  • 块表：chunks 是检索与引用的正文单元，可人工编辑，并有 chunk_revisions。编辑之后，检索看到的是块表，不一定再等于原文件。推断：对「被编辑过的块」而言，块表成为检索文本的实际来源。
  • 向量 / 关键词索引：按知识库绑定的引擎派生而来。重建索引可以删了再写；处理任务在删除旧块之前先解析向量存储，避免删完却写不进去。源码确认 internal/application/service/knowledge_process.go:481–514

洋葱分层

内核

  • 租户（workspace）→ 知识库 → 知识条目 → 块 →（可选）父块/子块、FAQ、生成问题、图谱。
  • 所有核心表带 tenant_id；任务执行要写入 WithExecutionTenant。
  • 会话保存检索与生成参数，消息保存 knowledge_references。

控制流

  • 入库：convert（DocReader / 网页 / 纯文本）→ 切块 → 写块表 → 向量化 → 可选摘要/问题/多模态后续任务。
  • 问答：历史 → 记忆召回 → 查询理解 → 并行检索（知识库 + 可选网页）→ 重排 → 合并 → TopK → 拼进消息 → 流式生成。
  • 失败靠 asynq 重试；最后一次重试才把知识打成 failed。解析轮次（attempt）防止过期任务覆盖新一轮。

适配器

Web UI、Go SDK、内置 MCP、IM 渠道、嵌入式聊天挂件、数据源连接器（飞书、Notion、GitLab 等）、可替换的 LLM / 嵌入 / 向量库 / 对象存储。这些都不是内核，但决定部署面。README 列出的后端与格式以产品说明为准，本文未逐个打通。作者宣称

术语
  • Knowledge / 知识条目：一篇文档或一条导入记录。
  • Chunk / 块：带偏移、类型、可选父块的检索单元。
  • Hybrid search：同一查询同时走向量与关键词，再按配置融合。
  • RRF：倒数排名融合。本仓库在混合模式下用加权 RRF，再除以理论最大值，把分数映射到 [0,1]。
  • Attempt：一次用户发起的解析轮次；重试共用同一 attempt，用户重新解析会开新号，旧任务必须退出。
  • Citation / 引用：生成前把通过筛选的块登记进模型上下文；消息里保留 knowledge_references。默认开启，可关。

它和 ai-memory 不在同一层：WeKnora 解决「组织文档如何被授权检索并引用」；ai-memory 解决「编码 Agent 的工作记忆如何跨工具保存为 Markdown」。二者可以同时用，不宜直接比星标或当成替代品。推断

两端控制流：入库任务与问答管道

点击节点或阶段卡片查看机制。

入库：ProcessDocument 状态机

任务载荷包含 tenant、知识库、知识 id、文件路径或 URL、语言、以及 Attempt。入口先注入执行租户，再读取知识行做校验。源码确认 internal/application/service/knowledge_process.go:3856–3991

  • 知识不存在：直接成功返回（不再重试）。
  • attempt 已被更新的一轮取代：跳过，避免旧任务改新一轮的块和计数器。
  • parse_status 为删除中或用户取消：退出。
  • 已经 completed：幂等跳过。
  • 先前 failed：目前允许再试（注释写「暂时允许重试」）。
  • 知识库易主或租户不一致：SkipRetry。
  • 在把状态翻成 processing 之前再查一次取消，关闭「取消与状态写入」之间的窗口。
  • 文件路径变化或源被替换：跳过陈旧任务。
  • 图片未开多模态、音频未配 ASR：失败且不重试；视频在本提交明确不再支持入库解析。

文件 URL 导入会再次做 SSRF 校验、下载、写入对象存储，再进入 convert()。下载失败在非最后一次重试时返回错误以触发重试，最后一次才把知识标记 failed。源码确认 internal/application/service/knowledge_process.go:4044–4070

processChunks 会先清洗非法 UTF-8，再解析嵌入模型和向量存储——如果先删旧块再发现引擎不可用，文档会处于「旧索引已没、新索引也没有」的中间态，所以源码把解析顺序写在清理之前。源码确认 internal/application/service/knowledge_process.go:423–514

问答：实际组装的管道（不是文档里那张便利表这么简单）

types.Pipeline["rag_stream"] 是一份便利查找表。线上 KnowledgeQA 用 PipelineBuilder 按特征动态组装。有知识库范围或开启网页搜索时，实际顺序是：源码确认 internal/application/service/session_knowledge_qa.go:195–238

[LOAD_HISTORY?] → MEMORY_RECALL → QUERY_UNDERSTAND → CHUNK_SEARCH_PARALLEL → CHUNK_RERANK → [WEB_FETCH?] → CHUNK_MERGE → FILTER_TOP_K → [DATA_ANALYSIS?] → INTO_CHAT_MESSAGE → CHAT_COMPLETION_STREAM

没有检索范围且未开网页搜索时，退化为纯聊天：可选历史 + 记忆召回 + 流式生成。附件内容在这条路上直接拼进用户消息；RAG 路上则在 INTO_CHAT_MESSAGE 处理。

检索插件会并发打知识库与网页搜索；知识库失败但网页仍有结果时记警告并继续，两边都空才返回「什么都没搜到」。召回偏少且打开查询扩展时，会再跑一轮偏关键词的扩展。源码确认 internal/application/service/chat_pipeline/search.go:62–162

混合检索与融合

HybridSearch 先规范化 MatchCount（0 或负数会落到默认 50，并封顶），取出融合后的候选，再截断并做上下文 enrich。源码确认 internal/application/service/knowledgebase_search.go:183–200

  • 仓库层按 ID 取知识库是「故意不按租户过滤」的，以便加载组织共享、属于其他租户的库；但随后必须对每一个库做 authorizeKBAccess，否则调用者只要塞入别人的 UUID 就能打到对应向量存储。源码确认 internal/application/service/knowledgebase_search.go:225–248
  • 跨库必须通过同一嵌入模型校验（wiki/graph 库有例外）。查询向量只算一次，再按 (storeID, 所属租户) 分组扇出。
  • 过检量是 max(MatchCount*5, 50) * 库数量，再封顶，给融合和 FAQ 迭代留池子。
  • 融合：只用向量时保留余弦分；只用关键词时把 BM25 按该列表最大值缩放到 [0,1]（否则会撑死后面的合成分数和 MMR）；混合时用加权 RRF，再除以 (vectorWeight+keywordWeight)/(k+1)，使「两路都排第一」的块得 1 分。默认 k=60，向量权重 0.7，关键词 0.3。源码确认 internal/application/service/knowledgebase_search_fusion.go:48–176 与 internal/types/retrieval_config.go:92–118
反常识：混合检索的原始 RRF 总分大约只有 0.016 量级。若不做「除以最大值」的归一化，这些块在和「向量-only / 关键词-only」结果（分数已在 [0,1]）一起排序时会全面落败，重排和 MMR 也几乎看不到相关性信号。这是源码注释里明确写出的历史缺陷与修复。

最短成功路径与失败路径

成功

  1. 租户已配置嵌入模型与向量存储，知识库绑定它们。
  2. 上传被接受，知识行进入 pending/processing，asynq 投递 ProcessDocument。
  3. 解析与切块成功，块表与索引写入，parse_status=completed。
  4. 提问走 RAG 管道，混合检索命中块，重排与 TopK 后登记引用，流式生成并写入 knowledge_references。

失败 / 降级

  • 嵌入模型被删或停用：本轮解析在取模型时失败并记录原因，而不是一直停在 processing 直到清扫。
  • 向量存储解析失败：属「找不到」可重试；属写入/不可用则失败该知识。
  • 用户取消、删除、更换源文件、发起新 attempt：旧任务退出，不覆盖新数据。
  • URL 被 SSRF 规则拒绝：失败且不重试。
  • 检索管道中知识库失败但网页有结果：部分失败，仍可能回答，只是引用可能主要来自网页。
  • 两路检索都空：Search 插件返回 ErrSearchNothing，不会若无其事地编造引用。
  • 引用正文无法核验：提示模型不要引用或推断不存在的证据。

关键表、权限隔离与任务

初始关系见 migrations/mysql/00-init-db.sql:9–230。部署还包含 PostgreSQL / ParadeDB / SQLite 的版本化迁移，字段会随版本增加，但核心身份关系保持一致。源码确认

租户与知识库隔离

  • 认证中间件把调用者的租户放入上下文。访问路径里的租户时：自己的主租户永远允许；否则查成员关系，禁止仅凭「当前执行租户」去碰别人的库。源码确认 internal/middleware/access.go:61–90
  • 混合检索对每个目标知识库单独授权，包括组织共享库。注释写明：在别人租户里执行，并不等于可以看见该租户的其他库。
  • 后台任务用载荷里的 TenantID 设置执行租户，并用 WithKBTaskWrite 校验知识库仍属于该租户，防止处理过程中所有权变化。
  • 多角色 RBAC、作用域 API Key、OIDC、凭证加密、SSRF 与可选白名单，是 README 宣布的安全面；本页只把源码里能直接读到的检索与任务路径写死，其余按产品说明看待。作者宣称

不变量（从实现里抽出）

  1. 没有知识库或网页范围，就不要走检索管道。
  2. 跨库检索必须先授权、再校验嵌入空间一致，查询向量只计算一次。
  3. 清理旧块与旧索引之前，必须先能解析到写入用的向量引擎。
  4. 过期的 process 任务不得改写更新一轮 attempt 的行、块和计数。
  5. 融合后的分数在进入跨检索比较或重排之前，应落在 [0,1]（混合路径靠归一化 RRF）。
  6. MatchCount 的缺省、过检与最终截断必须用同一套规范化规则，避免 0 把结果切成空切片。
  7. 生成用的引用集合以管道过滤后的结果为准，并应告诉模型「这可能只是候选池的子集」。

并发、一致性、安全、成本、规模

  • 并发：文档处理在 worker 池里并行，同一知识的新 attempt 会让旧任务变成空操作。问答检索按存储分组扇出，知识库搜索与网页搜索并发。插件式 EventManager 按注册顺序包装 handler。
  • 一致性：原文件、块表、向量索引可能暂时不一致——这是异步系统的常态。幂等清理会在重跑时删除旧块和旧索引再写新的。块被人工编辑后，检索文本以块表/修订为准，原文件不会自动改写。推断
  • 安全：租户授权发生在检索扇出之前；URL 导入有 SSRF 复查；日志会清洗查询文本以防 CR/LF 注入。凭证与模型密钥处理有专门模块，本页不展开密钥格式。
  • 成本：问答路径几乎总需要聊天模型；向量检索需要嵌入。摘要、问题生成、重排、多模态、图谱抽取都是额外调用。与 ai-memory 的「默认零 LLM」相反，这里的完整成功路径通常是付费/自建模型路径。推断
  • 规模：过检池有上限；FAQ 路径还能迭代扩大 TopK。任务仪表盘与 worker 池权重在 types/task.go 中定义。具体能撑多大的知识库，README 没有给出可引用的本机数字，本文也不编造。待验证

多模态与外部依赖

知识库带 image_processing_config、vlm_config；音频依赖 ASR；视频在本提交的 ProcessDocument 中直接失败。解析依赖 DocReader（Office 由 README 所称的 in-process anydoc 处理，本文未逐步跟进 anydoc 源码）。向量库、对象存储、可选 Neo4j、Langfuse、沙箱（Docker/E2B/Cube）都是可替换或可选组件。缺了对应组件，对应分支会失败或跳过，而不是在本进程里静默伪造。源码确认 视频/ASR 分支；其余后端列表为 作者宣称。

最小反例

  • 跨两个使用不同嵌入模型的知识库做一次 HybridSearch：会被一致性检查拒绝，而不是悄悄给出不可比的分数。
  • 只把别人的 knowledge_base_id 塞进参数：授权失败。仓库层「能读到行」不等于「能检索」。
  • 以为 types.Pipeline["rag_stream"] 就是线上路径：会漏掉 MEMORY_RECALL，也会漏掉按开关插入的 WEB_FETCH / DATA_ANALYSIS，以及「有历史才 LOAD_HISTORY」。
  • 在解析过程中删除嵌入模型：任务应失败并写明原因，而不是悬挂在 processing。
  • 把 WeKnora 当成「编码 Agent 的跨工具工作记忆」：它可以给 Agent 提供知识检索工具，但不会替 Claude Code / Codex 做会话级 Markdown 记忆与交接协议。

不适用

单机、默认不配模型、只想让几个编程 Agent 共享一份可 grep 的项目笔记时，它太重。也不是离线即可用的纯文件 wiki：生成与（通常情况下的）向量检索都依赖模型与外部存储。

最小接入实践

  1. 按 README 用 Docker Compose 启动核心服务，完成引导里的模型与存储配置。默认 Web 在本机 80 端口、API 在 8080，这是文档中的端口，本文未在本机启动验证。作者宣称 待验证
  2. 先建一个知识库，明确嵌入模型、切块策略、是否父子块、是否启用向量/关键词。
  3. 上传一份小的纯文本或 Markdown，盯 parse_status 直到 completed，并在界面或 API 里抽查块内容和修订。
  4. 用同一句话先打 HybridSearch（不生成），确认命中和分数；再走一次带引用的问答。
  5. 需要多用户时再配置成员角色与 API Key 作用域，不要把管理密钥发给客户端。
  6. 打开网页搜索、多模态、图谱、沙箱前，先单独验证对应依赖和 SSRF/网络策略。

落地核对清单

  • 每个知识库的嵌入模型与向量维度是否与目标引擎一致？
  • 对象存储、数据库、向量引擎失败时，是否能从任务仪表盘看到重试与死信，而不是只有「处理中」？
  • 共享库是否走了授权，而不是只把 UUID 加入检索列表？
  • 块被编辑后，是否重建或更新了对应向量？旧索引会不会继续回答过时句子？
  • 引用开关是否符合产品要求？关闭后模型上下文的协议提示与公开引用都会变。
  • 升级是否让版本化迁移先跑完，再让 worker 接管积压任务？

误区自测

1. 知识库表里有了文件路径，是不是就已经可以混合检索了？
检索单元是块以及派生索引。知识行只是文档身份和解析状态。
2. 混合检索时，为什么要把 RRF 分数除以理论最大值？
fuseWithRRF 的注释把这个缺陷和修复写得很清楚。单路路径不走 RRF：向量保留余弦，关键词单独缩放。
3. 一次问答请求一定会执行 types.Pipeline["rag_stream"] 里写死的阶段吗？
以 session_knowledge_qa.go 为准。便利表会漏掉记忆召回和若干条件阶段。

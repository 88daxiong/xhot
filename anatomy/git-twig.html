git-twig：给 Agent 用的写时复制工作树

物理本质：它不是另一种 Git。它只在「源工作区当前 HEAD、文件系统支持克隆、检出不会改写字节」这一窄带里，把已提交文件做成私有的写时复制副本，再交给 Git 去登记成普通 linked worktree；其余情况原样调用 git worktree。

唯一事实来源与不可替代闭环

底牌：什么被当成“正确的工作树”

SSOT = 源仓库对象库里、当前 HEAD 指向的那棵树
         + Git 自己的 worktree 登记元数据

Entry（来自 git ls-tree -rlz --full-tree）:
  path, kind(File/Symlink/Submodule),
  object（blob/commit id）, blob_bytes

不进入 SSOT 的东西：
  工作区未提交改动、ignored 文件、
  源根上的 .git 与清单外目录

暂存位置: $GIT_COMMON_DIR/twigs/staging
登记锁:   $GIT_COMMON_DIR/twigs/registration.lock

暗逻辑：先克隆，再证明克隆等于对象

真正不可替代的不是 CLI，而是这条闭环：源码确认

  1. 只根据提交清单克隆，而且是 CoW / 新文件，不用硬链接绑住源工作区。
  2. 用 hash-object --no-filters --stdin-paths 对私有副本做哈希，跟对象 ID 比；不走会清洁过滤的索引哈希。
  3. 不能证明恒等的路径（换行转换等）改回 Git 写；带外部 filter 的直接放弃原生路径。
  4. 最后仍由 git worktree add --no-checkout 完成分支校验与登记，产出的是普通 linked worktree，后续 git 命令不必知道 twig。

和「直接 git worktree / 硬链接 / 再 clone 一份」的差别

做法空间正确性边界说明
git worktree add按文件再写一份推断Git 自己的检出语义最完整twig 在不满足门禁时就走这条。作者公布的基准里，小仓库上 Git 往往明显更快作者宣称
硬链接工作区很小写一个检出可能改到另一个源码明确用 clonefile / FICLONE + create_new，避免与源文件共享 inode源码确认
再 clone / 浅克隆对象库再来一份独立仓库，登记模型不同twig 要的是同一对象库上的廉价工作树，给并行 Agent 用作者宣称
git-twig 原生路径作者表称可少约 1.9× 到 155×作者宣称仅 HEAD、可克隆 FS、可证明恒等或交 Git 写的路径典型 ext4 无 reflink 时会回落源码确认。本文未复跑基准待验证

故事板：小区复印室的「影子复印」

硬核边界仍以上一栏的状态机为准；这个同构只帮助记住「为什么不能随便省空间」。

物业想给每个装修队发一套图纸。要是每次都把整柜图纸再印一遍，储藏室很快会堆满——这就是普通 git worktree 的全量写出。

这栋楼的复印机有一项特殊能力：先做一份「影子复印」，纸还是同一叠纤维，只有你在自己桌上涂改时才会另外长出新页。这就是写时复制。但管理员定了死规矩：只能复印你此刻摊在桌上的那一版（必须是 HEAD），不能凭记忆去印上个月的版本；印完还要抽查页码是不是和档案柜里的原件一致（裸对象哈希）；需要改尺寸、换页眉的特殊文件，必须交给原厂印刷机（Git 写出）。

如果这层楼的复印机根本没有影子功能（典型 ext4），或者档案柜和你的工位不在同一栋楼（跨文件系统），就只能老实整份再印。印到一半停电，半成品要留在工作台上让人检查，不能当没发生过。

原系统概念故事里的对应物第一性原理作用
源工作区当前 HEAD 的已提交树桌上正在翻的那一版图纸原生 CoW 的唯一可读来源；别的修订没有对应的现成文件可克隆
clonefile / FICLONE影子复印共享物理块，写入时才分裂，且不通过硬链接改到原件
hash-object --no-filters对照档案柜抽查页码证明副本字节等于对象库，而不是等于「过滤后的工作区印象」
GitWrite / stock git worktree原厂印刷机凡是会改写字节或语义不清楚的路径，把正确性交还给 Git
失败后保留的 staging / 半登记工作树留在工作台上的半成品登记一旦开始就不能假装无事；必须人工检查再重试

取舍、失效边界与最小落地

崩溃与回落边界
  • 原生路径不做 Windows；非 macOS/Linux 会直接走 Git。源码确认
  • 典型 ext4（无 reflink）、跨盘、源/目标/Git 元数据不在同一设备，不能原生 CoW。源码确认
  • 指定非当前 HEAD 的修订、sparse checkout、子模块、core.symlinks=false、replace/grafts、部分 hooks、外部 filter，都会放弃原生路径。源码确认
  • git worktree add --no-checkout 一旦执行，失败会留下已登记的部分工作树和暂存目录。源码确认
  • 本地未提交改动和 ignored 文件本来就不会被带上——这是设计，不是漏拷。源码确认
  • 作者自己的基准表明：小仓库上 twig 可以比 Git 慢一个数量级，换来的是空间；「最多少占约 97%」是宣传口径，具体数字随仓库与批次数变化。作者宣称 本机未复跑。待验证

最小落地建议

  1. 先确认文件系统：macOS/APFS，或 Linux 上的 Btrfs / 开启 reflink 的 XFS。不确定就设 TWIG_TRACE=1 看它是否选择了原生路径。作者宣称 源码确实在该环境变量下打印后端选择。源码确认
  2. 按上游 README 用 Homebrew 或 cargo install git-twig --locked 安装，并核对自己要的版本标签；不要用来路不明的安装脚本。
  3. Agent 侧只用于「从当前 HEAD 并行开工作树」：git twig new -b feat/x ../feat-x HEAD。需要检出别的提交，接受走 Git。
  4. 并发创建时依赖它自己的登记锁；不要在创建过程中手动扭目标目录或改 worktree 配置。
  5. 失败后先看 .git/twigs/staging 和 git worktree list，清理半成品再重试。

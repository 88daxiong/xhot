Mingle

你在本机创建一个有名字、角色和记忆的 Agent，由已经登录的 Claude Code、Codex 等编码代理驱动；它以机器人身份出现在你正在用的聊天软件里。Mingle 没有自己的服务器，也不自己实现模型循环。

最大亮点

一等对象是长期存在的 Agent，不是某个聊天软件里的一次会话。所有 IM 的消息都进入同一条可恢复的 harness 会话；连续性来自这条会话和 MEMORY.md，而不是再造一个聊天平台。

常见做法要么自建工作区和服务器（如 Raft），要么在 IM 里用命令去操控某个终端会话。Mingle 把已有的官方机器人通道接到本机已付费的编码代理上：控制台和 API 只监听 127.0.0.1，机器人凭据进系统钥匙串，模型登录态仍由各 harness 自己管。源码确认

一句话输入输出：输入是某个已连接聊天里的一条消息（或提醒、交接）；输出是同一条会话里的模型回合，以及经权限检查后、通过 mingle 命令送回原聊天的回复。机器需要保持运行，并已安装、登录所选 harness。

怎么用

什么情况下用

  • 已经在用 Claude Code、Codex、OpenCode 或 Kimi Code，希望同一个 Agent 出现在飞书、Slack、Telegram 等现有对话里，并且记得跨软件发生过的事。
  • 不想把聊天记录交给第三方 Mingle 服务器，也不想再学一套新的工作区产品。
  • 可以接受：电脑（或你自己的 SSH 主机）要在线，消息仍会经过 IM 平台和模型厂商。

什么情况下不用

  • 需要现在就把微信、钉钉等通道当成已经在真实租户里验证过的产品能力。作者写明核心端到端目前在 Claude Code / Codex / OpenCode / Kimi Code 上工作；飞书在真实租户验证过，其余聊天软件主要是对接官方 API 和测试。作者宣称
  • 不能接受「一个 Agent 的记忆跨群共享」：私聊里听到的内容，可能在群里被说出来。这是规格里已接受的取舍。源码确认
  • 希望 Mingle 自己提供模型、账号或多设备云同步。这些明确不在范围内。

最小上手方案

从 Releases 安装桌面应用（macOS 已签名公证；Windows 尚未签名），或在已有 Node.js 24 和 pnpm 的机器上从源码启动。分析所用版本是 0.3.1：

git clone https://github.com/earayu/Mingle.git && cd Mingle
git checkout 58559b332b80493c0caf6956282e0c35200a0879
pnpm install && pnpm build
node dist/cli/main.js start
node dist/cli/main.js agent create --name Alex --harness claude --role "You help me plan trips."
echo "$TELEGRAM_BOT_TOKEN" | node dist/cli/main.js connect alex telegram
  • 桌面应用安装脚本见 README；控制台只绑在本机回环地址。源码确认
  • 谁扫码或向机器人发送 6 位认领码，就成为该 Agent 的 owner。之后 owner 可用 /stop 叫停当前回合。作者宣称
  • 本文只阅读了源码、规格、测试目录和 Changelog，未在本机启动桌面应用，也未连接任何聊天租户。待验证

深入

下面这些不影响先建立整体图景。需要对照源码、字段或边界时再展开。证据仍指向固定提交 58559b3。

入站状态机：消息如何从收到变成已回复
  • inbound.ts 把入站消息写成有限状态：received → delivered / waiting / failed / unanswered / replied / ignored / held。例如 deliver 只从 received 走到 delivered；Agent 的 reply 可以从多种未完成状态走到 replied；普通 send 不能把从未送达的失败消息悄悄标成已回复。源码确认
  • 群里没被 @ 的背景消息、暂停期间的消息，以及 owner 拒绝的私聊/进群请求，不会唤醒回合。Owner 在群里的唯一会话命令是 /stop。源码确认
投递：空闲合并、运转中插入，或排到下一回合
  • AgentRuntime 在空闲时把短时间里的多条消息合成一次新回合；回合进行中则把新输入 steer 进当前回合，若 harness 不支持插入就 queue 到下一回合。源码确认
  • 投递结果是 prompted | steered | queued | rejected。Kimi Code 会在自启后台任务未结束时立刻给出空回合，0.2.3 起这种空回合不算真正作答，消息继续等待真正跑模型的那一轮。源码确认
  • 若一个回合对正在等待回复的消息连续 20 分钟没有任何思考、正文、工具、子代理或 mingle 命令，运行时会自行结束该回合并换进程，避免状态一直停在「工作中」。无人等待的长任务不会被这条规则打断。源码确认
会话可丢，Agent 不丢
  • 每个 Agent 只有一条长期 harness 会话，工作目录就是它的主目录。重启后用 OAR 的 resume 恢复同一会话 ID；会话损坏或更换 harness 时再开新会话，靠 MEMORY.md 和消息记录接上。源码确认
  • 冷启动默认关闭。空闲超过 1 小时、上下文超过 128K token、且这次不是插话时，可按 MINGLE_COLD_START=rebuild 新开会话，第一条输入由 Mingle 组装：MEMORY.md 开头约 16 KiB、最近 25 条跨聊天消息、近 2 小时改过的文件路径、最近 15 个工具动作，再加上触发这一次的输入。被替换的会话 ID 留在 agents.previous_session_id，新会话打开失败则继续指向旧会话。源码确认
  • 和 harness 的唯一接触点是 src/harness/harness.ts，它封装 @botiverse/oar 0.97.0。对不支持追加系统提示的 harness，引导说明改放在新会话的第一条消息里。源码确认
数据放在哪，密钥不进数据库
  • 运行状态在 ~/.mingle/mingle.db（Node 24 自带 node:sqlite）。角色、记忆和笔记是主目录里的普通文件，可以用编辑器和 git 管理。源码确认
  • IM 凭据和 Agent 环境变量的值走 defaultSecrets：macOS 用 Keychain，Windows 用当前用户 DPAPI，Linux 优先 Secret Service；数据库只存引用或名字。控制台 API 只听 127.0.0.1。源码确认
  • 规格写明：消息必然经过 IM 平台和模型厂商，这不在「没有 Mingle 服务器」的承诺里；跨群记忆不隔离是为了保持「一条会话」的简单模型。源码确认
和替代方案比，以及已知失效边界
  • 与 Raft 相比：学了它「长期进程 + MEMORY.md」的模型，但不自建频道和服务器。与 dsh-im、cc-connect 相比：不绑定单一 harness，也不把会话命令暴露到 IM 里。作者宣称
  • 规格第 12 节记录了飞书真实租户上的多项通过项（私聊、群 @、离线补推、同群两个机器人去重等），也记下了未完整通过或仍待验证的项：例如早期 /stop 后后台任务仍可能回复（后续有模拟聊天复测，飞书真机回归仍待验证），以及需要管理员审核的租户表现。作者宣称 本文未复现这些实测。待验证
  • Remote SSH（把 Agent 放到你自己的另一台机器上）在 0.2.0 已出现，规格仍将其标为开发中的能力，完整稳定性以仓库当前说明为准。作者宣称
  • 仓库有大量单元测试（含 flow.test.ts、harness.test.ts、inbound.test.ts、feishu.test.ts 等）和 pnpm check 脚本。本文没有运行测试套件。待验证

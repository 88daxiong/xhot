WeKnora

腾讯开源的企业文档知识框架：把资料收进自己的环境，做成可以检索、可以引用、也可以交给 Agent 继续办事的知识库。

仓库 Tencent/WeKnora 站点 weknora.weixin.qq.com 分析提交 7d064bc（2026-11-16 21:29 北京时间） 许可证 MIT（仓库另有第三方声明） 单文件版 下载
最大亮点

企业文档问答在生成答案之前，会登记可核对的引用；并且检索前必须先按租户完成授权。

它不只是「把文档切块再丢给大模型」。原文件留在对象存储，切块才是检索单位；真正上线的问答路径由流水线按开关组装。仓库读取知识库时不过滤租户，所以授权这一步不是附加功能，而是正确性的前提。源码确认

一句话输入输出：输入是文档（或已有知识库）加上用户问题；输出是带出处的回答，以及可选的后续 Agent / 百科整理。它和 ai-memory 不在同一层：一个管组织文档，一个管编程 Agent 的工作记忆。

怎么用

什么情况下用

  • 要把制度、手册、资料做成能回答、能指出处的知识库，并希望数据留在自己的环境。
  • 需要多知识库、多成员，而且必须按租户或工作空间隔离。
  • 还想把同一套知识库接到 Agent、IM 渠道或内部网站。

什么情况下不用

  • 主要需求是给编程 Agent 记下「上次做到哪」——那是 ai-memory 的场景，不必先上整套文档平台。
  • 本版本明确不支持视频文件入库；图片需要多模态，音频需要语音识别。
  • 暂时无法提供聊天模型和嵌入模型，又希望跑完整的文档问答。

最小上手方案

官方自托管入口写在本分析提交的 README「Run with Docker Compose」，以及站点上的 Quickstart。该文档要求先安装 Docker、Docker Compose 和 Git，然后执行：

git clone https://github.com/Tencent/WeKnora.git
cd WeKnora
cp .env.example .env
docker compose pull
docker compose up -d
  • 随后打开 http://localhost，按引导完成初始配置。文档列出的地址是：网页界面 http://localhost，后端 API http://localhost:8080，Langfuse 追踪 http://localhost:3000。作者宣称
  • 本提交的 .env.example 里，WEKNORA_VERSION=latest。按官方升级说明，若要贴近本页分析的 0.9.0，可在 .env 里把它改成 0.9.0，再执行 docker compose pull 与 docker compose up -d。只执行 up -d、不先 pull，可能继续使用本地缓存的旧镜像。作者宣称
  • 验证标准（官方路径，本文未执行）：浏览器能打开引导页；配置模型后，上传一份小文档，问一个文档里有的问题，回答应带得出处。待验证
  • 官方还提供云端平台、云服务器模板、Helm 以及轻量单二进制等部署方式，见同一 README 的 Other ways to deploy。上面五条是文档写明的标准 Compose 起步路径。本文未在本机执行克隆以外的安装或启动。

深入

下面这些不影响先建立整体图景。需要对着源码看流水线、融合公式或隔离边界时再展开。

真源是文件，检索单位是切块
  • 对象存储中的原文件是这份资料的真源；知识行记录身份和解析状态；切块才是检索单位，而且切块可编辑、可对比、可回滚。编辑后的切块可能已经不同于原文件。
  • 向量索引和关键词索引都是派生数据。处理任务会在删除旧切块和旧索引之前，先解析好新的向量引擎，避免失败后无法回写。
  • 本提交在上传与处理两条路径上都拒绝视频：internal/application/service/knowledge_create.go:62–63，internal/application/service/knowledge_process.go:4033–4038。
上线的问答流水线是组装出来的

源码里虽有方便查阅的流水线类型，但会话问答实际走的是 internal/application/service/session_knowledge_qa.go:226–237 里的 PipelineBuilder。完整 RAG 路径是：可选加载历史 → 记忆召回 → 问题理解 → 并行检索 → 重排 → 可选联网抓取 → 合并 → 截取 TopK → 可选数据分析 → 写入聊天消息 → 流式生成。没有知识库时会走更短的路径，直接进入生成。

混合检索如何把分数放到同一尺度

internal/application/service/knowledgebase_search_fusion.go:48–114 写明：只开向量时保留余弦相似度；只开关键词时按该列表的最高分把 BM25 缩放到 [0,1]，否则原始 BM25 会把后续综合分顶满；两路都开时做加权 RRF，再除以最大值，使两路都排第一的切块得到 1 分。默认检索深度 DefaultRetrievalTopK = 50，见 internal/types/retrieval_config.go:40–44。

租户隔离为什么必须发生在授权这一步

internal/application/service/knowledgebase_search.go:236–253 解释：GetKnowledgeBaseByIDs 在仓库层有意不按租户过滤，以便加载组织共享、所有权属于其他租户的库。因此每个库都必须再走 authorizeKBAccess。源码写明，如果没有这道闸，调用方只要传入任意知识库 ID，就可能触及别人的向量库。执行租户上下文（WithExecutionTenant）用于工作线程按正确租户读写，但不能替代这步授权。

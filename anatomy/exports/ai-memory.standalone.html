ai-memory：以 Markdown Wiki 为真源的跨 Agent 记忆层

物理本质：它不是「又一个向量数据库」，也不是给模型的自动日记本。内核是一棵 git 版本管理的 Markdown 页面树：路径就是身份，编辑通过「取代（supersede）」留下版本链；SQLite 只是可重建的派生索引。默认路径不调用任何大模型——生命周期钩子静默采集、会话结束用规则写成摘要页、下一次会话用全文/实体/链接（可选向量）融合检索，并把有界的简报注入新会话。

它到底在解什么问题

编程 Agent 的「记忆」通常绑定在单一产品里：Claude Code 自己记笔记，Cursor 自己记上下文，换一个 CLI 或换一台电脑，这些笔记就看不见了。README 把这一点说成核心动机：记忆要能跟着人跨越 Agent、项目与机器，并且对团队可共享。作者宣称

从源码看，它选择的解法不是「把对话全文塞进向量库」，而是把长期记忆建成 Karpathy 风格的 LLM Wiki：磁盘上的 Markdown 是唯一内容真源，SQLite 负责检索、会话、观察、交接、审计和可选嵌入。源码确认 见 docs/ARCHITECTURE.md:16–21 与 README.md:739–758。

和普通笔记、普通向量库差在哪

方案真源采集召回后怎么用跨工具
手写笔记 / Obsidian文件人写人打开或自己检索与 Agent 无关
单一 Agent 的 Memory 功能该产品内部存储该 Agent 自己记只在该产品里注入换工具即失效
通用向量 RAG常以切块+向量为检索主索引文档导入把切块拼进提示，生成答案作为知识库服务，不理解会话生命周期
ai-memory（本提交）git 管理的 Markdown 页面；数据库可重建钩子采集观察，会话结束编译成页面；也可 MCP 手写有界简报注入 + 混合检索；默认不调用 LLM 生成「答案」多种 CLI 钩子与 MCP 共享同一服务器

可选嵌入存在于 SQLite，而不是独立向量库；且 {provider, model, dim} 与每条向量绑在一起，模型一换就忽略旧向量。源码确认 不变量第 8 条 docs/ARCHITECTURE.md:1201–1203。作者说「没有要维护的向量库」，指的是不必另起一套向量服务，并不是「系统里没有向量」。作者宣称 + 推断

洋葱分层

内核

  • 页面身份是三元组 (workspace_id, project_id, path)，从初始迁移就写进每张领域表。
  • 同一路径同时只有一行 is_latest=1；内容变化就新开一行并 supersedes 旧行。
  • 观察（observation）是会话里的原始事件；页面是编译产物。二者不是同一层对象。
  • 交接（handoff）是有主人、只被领取一次的协议对象，不是又一篇摘要。

控制流

  • 所有写入走单一 SQLite writer 线程（mpsc）。
  • 索引与数据在同一事务提交。
  • 会话结束：规则生成 sessions/<id>.md、写入自动交接、标记会话结束，在同一事务里完成数据库侧效果，再自动提交 wiki。
  • 检索：FTS5 + 实体 + 图邻居 + 可选向量，用 RRF（k=60）融合，后再做有界权威调整。

适配器

生命周期钩子（Claude Code、Codex、OpenCode 等）、MCP 工具面（如 memory_query / memory_write_page / memory_briefing / memory_handoff_*）、HTTP/Web、可选 LLM 用于会话整理、嵌入和「dream」。管理控制台要同时打开编译特征与运行时开关。源码确认 crates/ai-memory-mcp/src/server.rs:11436–11457。

术语
  • Page / 页面：wiki 里一篇 Markdown，带 frontmatter、层级（working / episodic / semantic / procedural）。
  • Observation / 观察：一次钩子事件经净化后的记录，隶属于 session。
  • Supersede / 取代：同一 path 的新版本取代旧版本，旧行保留并 is_latest=0。
  • Tombstone / 墓碑：is_latest=0 且 superseded_at 有值，表示「存储认为这个路径现在没有文件」（衰减驱逐或对账删除），与普通历史版本不同。
  • Brief / 简报：会话开始时按预算注入的项目摘要，不是全库倒入。
  • OKF：页面 frontmatter 的规范形态，在唯一写入扼点被 conform。

架构：真源在文件，索引在库

一个 Rust 二进制拥有一个数据目录：wiki/、raw/、db/、models/、logs/。作者与架构文档反复强调：Markdown wiki 是真源，SQLite 是派生索引。源码确认 docs/ARCHITECTURE.md:36–39。

点击图中节点或下面的阶段卡片，查看对应机制。

采集、去重、冲突、删除

  • 采集：钩子把 SessionStart、UserPromptSubmit、PostToolUse、SessionEnd 等事件 POST 到 /hook。原生命令用稳定的幂等键本地暂存，再交给 drain。被最近标记策略丢弃的文件工具事件不会进入暂存、队列、传输、日志或存储。源码确认 docs/ARCHITECTURE.md:55–92
  • 更新 / 去重：upsert_page_in_tx 用 body SHA-256 加上去掉 generated.at 后的 frontmatter、标题、层级、置顶标志做短路径：完全一样就复用当前 id，只补证据。内容变了则把旧行 is_latest=0，新行 supersedes 旧 id。源码确认 crates/ai-memory-store/src/ops.rs:2164–2296
  • 条件写入 / 冲突：upsert_page_if 在同一事务里检查「路径不存在」或「最新版本仍是这个 id」，不满足则不写。批量版本一处失败则全部不写。这是并发下的乐观冲突处理，不是三路合并。源码确认 crates/ai-memory-store/src/ops.rs:305–351
  • 墓碑复活：若路径上已有带 superseded_at 的墓碑，新写入必须接上旧链并清除 superseded_at，否则之后的硬删除会把「曾经误删、文件又回来了」的历史链清掉。源码确认 crates/ai-memory-store/src/ops.rs:2304–2337
  • 删除：衰减驱逐把最新行打成墓碑；hard_delete_after_days 默认 180 天后可硬删整条墓碑链。会话清除（purge）会留下墓碑，阻止磁盘对账把已删会话摘要写回来。观察在巩固后可被修剪，而且作者写明：修剪后无法用更好的模型重新巩固，摘要页成为该会话仅存的叙述。源码确认 docs/ARCHITECTURE.md:263–268 README 说「没有东西会被硬删除，原件留在 git」——这描述的是页面编辑/整理默认不丢 git 历史；它不能否定库内硬删与观察修剪的存在。两者都要同时看。作者宣称

何时检索、何时注入上下文

检索入口是 hybrid_search_inner：先做实体命中和页面 FTS，若调用方提供查询向量再查正文嵌入和可选摘要嵌入，用这些种子扩展图邻居；默认还开启观察流，用原始观察文本给对应的最新会话页投票。源码确认 crates/ai-memory-store/src/reader.rs:8733–8911

融合公式是经典 RRF：score(d) = Σ 1/(k + rank_i(d))，k=60。若观察流已经给某会话页投票，该页的页面 FTS 贡献被置零，避免「标题里碰巧有几个主题词」压过真正命中观察正文的会话。源码确认 crates/ai-memory-store/src/reader.rs:8920–8950

反常识：向量流没有相似度下限。只要库里有任何嵌入，向量检索几乎会对每个查询返回若干页，图扩展还会跟着这些种子走。因此源码用「是否存在词法命中」（FTS、实体或观察流）来判断这是不是一次真正的匹配。源码确认 crates/ai-memory-store/src/reader.rs:8913–8918

注入发生在 SessionStart：若仓库标记打开了 [briefing] inject_on_session_start（查询也可带 briefing 标志），服务器按 max_chars 预算生成项目简报，标题为「ai-memory: project brief」。简报是有界数据包，不是把整个 wiki 塞进上下文。跨项目 profile 也可在会话开始注入，作为仓库规则文件之下的默认习惯。源码确认 crates/ai-memory-hooks/src/router.rs:3145–3482 附近。

MCP 的 memory_query 可以在检索命中之外再选配「回答合成」，但默认关闭，且需要配置 LLM；失败时退回只返回命中。源码确认 crates/ai-memory-mcp/src/server.rs:3757–3757 README「query_answer」一节。

一条信息如何写入，再在下一次会话被召回

下面是可逐步播放的控制流。右侧状态是模拟数据，用来看对象怎么变，不是仓库里的真实记录。模拟演示 每一步的机制说明则对应本提交源码。← → 翻步，空格 播放/暂停。

成功路径：钩子被接收 → 观察落库 → SessionEnd 生成页面并提交 git → 新会话注入简报或 memory_query 命中该页。失败路径见下一步清单。

最短成功路径与典型失败

成功

  1. 在项目目录安装钩子，服务器只绑回环，读到数据目录里的根令牌。
  2. Agent 正常工作，事件在 202 下被承认；幂等键防止重放重复插入观察。
  3. SessionEnd（或 idle_end / finalize-session）写出 sessions/<id>.md 并打开交接。
  4. 下次任意已接入的 Agent 在同一项目启动，拿到简报和待领取交接。

失败 / 降级

  • 服务器饱和：钩子收到 429，不在 Agent 热路径里死等。
  • 会话已绑定另一 Agent：409，且该判断走内存视图，不打数据库。
  • cwd 探测卡住（权限、死掉的网络盘）：2 秒截止，该事件失败，不拖垮整个服务器。
  • 没有可靠 SessionEnd 的客户端：必须显式 finalize-session，否则只能等空闲结束维护任务。
  • 进程在「下游效果尚未打完成标记」时崩溃：效果是至少一次，可能重复已经做过的 wiki/交接，而不是悄悄丢后半段。

关键字段与不变量

初始表在 crates/ai-memory-store/migrations/V01__init.sql:1–126。后续迁移增加有效窗口、嵌入、衰减、幂等键、实体、反馈等列；写入扼点仍是 upsert_page_in_tx。

交叉不变量（必须守住的规则）

  1. 配置只在启动时读一次。
  2. 单一 SQLite writer 线程；最后一个句柄丢弃时仍要排空并加入该线程。
  3. 索引与数据同一事务提交，禁止「先返回再后台建索引」。
  4. 领域行从第一天起带三元组身份。
  5. 钩子是即发即弃：脚本硬超时 ≤200ms；服务器立即 202 或饱和 429；会话冲突 409 例外。
  6. 隐私剥离是类型边界：只有 sanitize() 能构造已净化观察。
  7. LLM 结构化输出只用原生 JSON schema 模式。
  8. 每条嵌入旁边都有 {provider, model, dim}，不匹配就忽略。
  9. 会改磁盘的生命周期命令先检查是否有活进程；备份走服务器在线备份 API。
  10. 文件写入原子（临时文件 + rename + fsync）；wiki 的 git 打开时带 core.fsyncObjectFiles=true。
  11. 零 LLM 是默认路径。

以上摘自 docs/ARCHITECTURE.md:1165–1231。文档还列有「无全局单例」「provider 认证先于构造」等。

衰减公式（纯函数，默认不算 LLM）

λ = ln(2) / half_life_days retention = salience · exp(−λ_tier · age_days) + σ · ln(1 + access_count) · exp(−μ · days_since_access) · breadth breadth = 1 + breadth_weight · ln(1 + max(distinct_actors,1) − 1) 默认：λ=0.02（约 35 天半衰期），σ=0.6，μ=0.04，cold_threshold=0.20，hard_delete_after_days=180，breadth_weight=0

「被用过的记忆忘得更慢」来自第二项：打开、检索命中或沿链接到达会增加 access。广度权重默认 0，因此开启按操作者计数的表不会立刻改变历史分数。源码确认 crates/ai-memory-store/src/decay.rs:1–203。压缩、去重、按层曲线默认关闭；只加长保留期的访问加权默认开启。作者宣称 与配置注释一致，本文未跑衰减作业。

并发、一致性、安全、成本、规模

  • 并发：所有写操作排队进一个 OS 线程，避免 SQLite 多写者。条件 upsert 解决「读了最新 id 再写」的竞态。钩子侧用每项目/键的门闩串行化重叠重试。
  • 一致性：真源是文件 + git；库是派生。磁盘对账不能复活已被 purge 的会话页。SessionEnd 的交接插入、结束戳、覆盖观察计数在同一事务，避免恢复时只看到一半。
  • 安全：默认只绑回环；新的 init 会在数据目录生成根令牌，不写进 Agent 配置。净化在入库前发生。人文登录越过回环默认要求 HTTPS 姿态；--allow-insecure-human-auth 必须显式打开。仓库可用 [capture] 排除路径或改成允许名单。
  • 成本：默认零 API 调用。LLM 只升级摘要、语义检索和可选 dream/auto-improve。作者宣称写入上限约 700/s 是测出来的，本文未复测。作者宣称 待验证
  • 规模：一个数据目录只允许一个服务器。大规模观察修剪按批进行，以免长时间占写锁；SQLite 文件删数据后不一定缩小，但备份包会变小。

反常识设计

  • 默认不做 LLM 总结，也能工作。
  • 向量不是权威：没有词法命中就不算真正匹配。
  • 观察流会关掉同一会话页的 FTS 投票，防止标题词干扰。
  • 墓碑和普通历史版本刻意用 superseded_at 区分，复活必须接回旧链。
  • 破坏性整理（压缩、去重、按层丢弃）默认关；「用得越多留得越久」默认开。

最小反例（说明它不是万能记忆）

  • 两个服务器对着同一 data_dir 启动：违反「一目录一服务器」，索引与 git 会打架。
  • 把企业制度 PDF 知识库的期望套上来：它可以导入文档，但产品内核是 Agent 会话记忆与 wiki 页面，不是多租户文档平台。
  • 只开向量、关掉 FTS：查询仍可能因「无下限的向量命中」返回一堆不太相关的页。
  • 以为 purge 会话后，对账扫描磁盘就能把摘要救回来：upsert_page_from_disk 会检查 purged_sessions 并拒绝。
  • 在没有 SessionEnd 的 harness 里指望记忆「自动完整」：可能只有观察，没有会话页和交接，直到空闲结束或手工 finalize。

不适用

需要带引用的企业文档问答、多租户隔离、异步解析 PDF/Office、混合检索后重排序再生成——那是另一层系统（例如 WeKnora），不要把它和 ai-memory 当成直接竞品。ai-memory 适合「多个编码 Agent 共享同一份项目记忆，并且希望记忆是可 grep 的 Markdown」。

最小接入实践

  1. 单用户先在本机跑一个服务器，确认 ai-memory status 的认证状态（旧安装或 Docker 快速开始可能在开启 auth 前无认证）。
  2. 只对需要的仓库安装钩子；用 .ai-memory.toml 明确 workspace/project，避免目录被收进错误项目。
  3. 先不配 LLM，验证采集、会话页、交接和 memory_query。
  4. 需要跨机器时再把服务器放到可达位置，配承载令牌或用户账号；人文流量走 HTTPS 反代。
  5. 需要语义检索再配嵌入，并接受一次全量重嵌。
  6. 打开压缩/去重/dream 之前，先理解它们会改写页面（历史版本仍可恢复，但检索看到的是新正文）。

落地核对清单

  • 是否做到「一个数据目录只有一个 server 进程」？
  • 钩子是否从数据目录读令牌，而不是把令牌写进 harness 配置？
  • 目标仓库的 capture 规则是否排除了密钥、.env、大型生成物？
  • 所使用的 Agent 是否有可靠的 SessionEnd，否则是否安排了 finalize 或 idle_end？
  • 团队场景下，个人交接是否保持个人可见、项目知识才共享？
  • 备份是否包含 wiki（真源）以及服务器在线备份的数据库，而不只是复制可能正在写的文件？

误区自测

1. 一条观察写入 SQLite 之后，它是不是已经等于一篇可检索的 wiki 页面？
默认检索的主对象是页面（FTS 建在 pages 上）。观察流可以给会话页投票，但观察本身不是 wiki 真源。零 LLM 时也不会先等嵌入。
2. 两次内容相同的写入（只是 generated.at 不同）会怎样？
upsert_page_in_tx 比较 body_sha256 以及去掉 generated.at 后的 frontmatter。相同则返回旧 id，并可 insert_evidence。
3. 配置了嵌入之后，一次查询只命中向量、命中不了 FTS/实体/观察，算不算源码意义上的「词法匹配」？
见 hybrid_search_inner 对 lexical_match 的注释：向量一旦存在就会对几乎每个查询给答案。
